# Requisitos del módulo OERManager

> Fuente única de verdad de requisitos. IDs correlativos estables (`RF-NNN`, `NFR-NNN`, `PEND-NNN`): no se reutilizan ni se renumeran. Estados: `propuesto` / `aceptado` / `[PENDIENTE]`. Trazabilidad en [traceability.md](traceability.md).

## 1. Parámetros del entorno y decisiones bloqueantes

Los marcados `[PENDIENTE]` **no están decididos por el propietario**: no rellenar con conjeturas. Los marcados `Resuelto` (bloque §B del propietario, 2026-06-12) conservan su fila por trazabilidad.

## 2. Requisitos funcionales (RF)

| ID | Descripción | Prioridad | Estado | Criterio de aceptación |
| --- | --- | --- | --- | --- |
| RF-001 | El módulo gestiona items de clase `lrmi:LearningResource`: la vista maestra y todas las operaciones parten de ese filtro | Alta | propuesto | Listado en panel admin muestra solo items `lrmi:LearningResource`; consulta API por `resource_class` |
| RF-002 | Vista maestra en panel admin: tabla extendiendo el sistema de columnas/browse del core (≥4.0) con columnas propias y panel de detalle configurable | Alta | aceptado | Objetivo completo: columnas propias etapa (`educationalLevel`), materia (`about`), proyecto (`isPartOf`), licencia (`rights`) y una columna calculada de estado de integridad (RF-006), además de las nativas (título, clase, fecha); panel de detalle con edición inline de visibilidad (RF-003) y de alineamiento curricular (RF-004), más historial de curación (value annotations `dcterms`, RF-008/ADR-0002). **v1 ya implementada (TASK-003, ADR-0005):** columnas visibilidad/etapa/materia/alineamiento/licencia/modificado, drawer de detalle fijo (solo lectura) y curación de visibilidad; edición inline de alineamiento, columna de integridad e historial quedan para una iteración siguiente |
| RF-003 | Curación de visibilidad: cambiar público/privado usando el campo nativo del recurso (no flag propio), individual y por lotes | Alta | aceptado | Cualquier usuario con rol `editor` o superior (no basta con acceso al panel admin) puede cambiar visibilidad desde la vista maestra o el panel de detalle, individual y por lotes. La visibilidad queda fuera de la auditoría RDF (ADR-0002). **v1 ya implementada (TASK-003, ADR-0005):** toggle individual + lote con confirmación desde la vista maestra, reusando el permiso nativo de edición; la restricción explícita por rol `editor`+ (matriz rol×acción, NFR-003) sigue como mejora futura |
| RF-004 | Re-catalogación curricular: escribir valores RDF (resource values) apuntando a items-término del currículo existente, con previsualización, confirmación y reversibilidad | Alta | aceptado | Properties (ADR-0004): `lrmi:educationalLevel`/`schema:about`/`lrmi:teaches`/`lrmi:assesses`/`dcterms:relation`. Cardinalidad: múltiple en las cuatro properties (un REA puede tener varios items-término por propiedad). Roles: `editor` o superior para alineamiento curricular y tags; `global_admin`/`site_admin` exclusivamente para `schema:isPartOf` (proyecto), acción de gestor aparte (ADR-0004). Localización de los DefinedTermSet curriculares: ADR-0006 (`lrmi:educationalFramework`, configurable) |
| RF-005 | Re-catalogación por etiquetas (tags) como valores RDF según vocabulario elegido | Media | aceptado | Tags = ejes temáticos en `dcterms:relation`, **controlado** por un único `schema:DefinedTermSet` raíz, identificado por ID de item fijado en la configuración del módulo (ADR-0006). Roles: `editor` o superior |
| RF-006 | Comprobación de integridad: servicio que valida valores RDF (existencia, destino vivo, completitud) | Alta | aceptado | Campos a validar (ADR-0004): alineamiento (`educationalLevel`/`about`/`teaches`/`assesses`) vivo + licencia (`dcterms:rights`) presente. Definición de «completo»: si el item tiene asignada la plantilla REA (`resource_template`), completo = cumple los campos marcados como obligatorios en esa plantilla; si no tiene plantilla asignada, se aplica el mínimo (alineamiento vivo + licencia presente) |
| RF-007 | Estadísticas visuales del catálogo (cursos/etapas, materias, proyectos, licencias) con exportación CSV/PDF | Media | aceptado | Dimensiones (ADR-0004): etapa `educationalLevel`, materia `about`, eje `relation`, proyecto `isPartOf`, licencia `rights`. Gráficos: conteo simple por dimensión, cruce de 2 dimensiones (p.ej. materia×etapa) y % de completitud (RF-006). Export: CSV de los datos agregados detrás de cada gráfico (PDF se evalúa en una fase posterior) |
| RF-008 | Auditoría de las acciones de curación (quién, qué, cuándo) | Media | propuesto | Value annotations `dcterms` sobre el valor curado registran quién (`dcterms:contributor`), cuándo (`dcterms:modified`) y qué (`dcterms:provenance`) — ADR-0002. Properties exactas: `[PENDIENTE]` (PEND-005) |
| RF-009 | Catalogación IA-assistida: la IA **propone** alineamiento curricular y ejes temáticos a partir de los metadatos del item y del contenido de sus medios; el **curador confirma** | Alta | aceptado | La IA propone valores para `lrmi:educationalLevel`/`schema:about`/`lrmi:teaches`/`lrmi:assesses`/`dcterms:relation` como etiquetas que se resuelven a items-término del currículo (ADR-0007); las propuestas pre-rellenan el flujo de re-catalogación (preview + confirmación + auditoría) de RF-004/RF-005, nunca se escriben sin confirmación del curador. Reimplementación PHP inspirada en el REA-MCP-cataloguer (no se reusa como servicio externo). Resolución por búsqueda incremental, sin volcar el árbol curricular al LLM (NFR-004). Lote en segundo plano → RF-011 (tarea aparte) |
| RF-010 | Conexión a una API LLM **configurable por proveedor** (modelo local / Anthropic / OpenAI-compatible) | Alta | aceptado | El proveedor, endpoint/base URL, modelo y clave API se fijan en la configuración del módulo (ADR-0008). La clave vive en los settings nativos de Omeka; **nunca** en el repo, en el código ni en logs (CLAUDE.md §Seguridad). Abstracción por adaptadores; HTTP con `Laminas\Http\Client` del core, sin dependencia nueva |
| RF-011 | Catalogación IA-assistida **en lote** como Omeka Job en segundo plano: marcar varios items en la vista maestra y lanzar un Job que los catalogue con IA | Media | propuesto | Marcado múltiple en la vista maestra → `Omeka\Job` despachado al cola/runner nativo; cada item sigue el flujo propone→confirma o se deja la propuesta pendiente de revisión. **Tarea aparte de TASK-004** (no se implementa en TASK-004). Programación/scheduler a detallar en su tarea |
| RF-012 | Visión para imágenes en la cascada de extracción de contenido (configurable) | Baja | propuesto | La extracción de contenido para la IA podrá incluir el análisis de imágenes adjuntas mediante un modelo de visión, activable desde la configuración del módulo. Mejora posterior; fuera de TASK-004 |
| RF-013 | Modelar `dcterms:type` de los términos del currículo como recurso controlado (`skos:Concept`) en vez de literal | Baja | propuesto | Hoy la dimensión de un término se marca con un literal `dcterms:type` (confirmado 2026-06-24; ver docs/referencia/curriculo-modelo-rdf.md). Migrarlo a `skos:Concept` da un vocabulario de tipos enlazable y sin erratas. Afecta al dato del currículo (que el módulo **consume**, no posee) y al re-catalogador, cuyo filtro pasaría de `eq` (literal) a `res` (resource). Mejora posterior |
| RF-014 | Acotación contextual del re-catalogador por el grafo curricular | Alta | aceptado | El re-catalogador acota cada dimensión hija por el ancestro ya elegido siguiendo el grafo LOMLOE (ADR-0009): cascada Etapa→Curso (`lrmi:educationalLevel`)→Asignatura (`schema:about`)→{Saberes (`lrmi:teaches`), Criterios (`lrmi:assesses`)}, con fallback por curso/etapa vía enlaces denormalizados. La Etapa es ayuda de navegación, no se escribe en el REA. Siempre con filtro `dcterms:type` + búsqueda incremental (NFR-004) |

## 3. Requisitos no funcionales (NFR)

| ID | Descripción | Prioridad | Estado | Criterio de aceptación |
| --- | --- | --- | --- | --- |
| NFR-001 | Extender el core, nunca parchearlo: integración solo vía `attachListeners`, `module.config.php` y mecanismos nativos | Alta | aceptado | `git diff` del core de Omeka vacío; guardrail PreToolUse activo en `.claude/settings.json` |
| NFR-002 | Sin tablas Doctrine propias (decisión del propietario); única excepción evaluable: auditoría (PEND-006) | Alta | aceptado | No existe `data/` con entidades ni migraciones propias, salvo ADR que documente la excepción |
| NFR-003 | Autorización por ACL nativa: privilegios propios vía `acl_resources`, `userIsAllowed()` en cada acción de curación | Alta | aceptado | Matriz rol×acción: visibilidad, alineamiento curricular y tags → rol `editor` o superior; proyecto (`schema:isPartOf`) → `global_admin`/`site_admin` exclusivamente. No se añaden restricciones más allá de las que ya impone el core de Omeka por encima de esos roles |
| NFR-004 | Rendimiento: la selección curricular del re-catalogador no carga el árbol completo (lazy-load/búsqueda incremental) | Alta | aceptado | Siempre búsqueda incremental desde el primer item-término (autocomplete), sin umbral numérico que mantener: nunca se carga el árbol curricular completo de golpe |
| NFR-005 | i18n: cadenas traducibles vía Laminas; idiomas al menos es/en | Media | aceptado | Cadenas traducibles vía Laminas; idiomas soportados: español e inglés |
| NFR-006 | Accesibilidad: mantener el nivel del admin de Omeka 4.x | Media | aceptado | Nivel objetivo = el que ya ofrece el admin nativo de Omeka 4.x, sin objetivo WCAG adicional específico del módulo |
| NFR-007 | Compatibilidad: mínimo Omeka-S 4.2 (`omeka_version_constraint = ^4.2.0`) y PHP 8.4 (uso interno; revisar si se publica al ecosistema) | Alta | aceptado | `config/module.ini` declara `^4.2.0`; `composer.json` declara `php >= 8.4`; el módulo instala y corre en Omeka-S 4.2 con PHP 8.4 |
| NFR-008 | Clasificación IA óptima: maximizar accuracy y minimizar consumo de tokens del LLM; ante conflicto, **prima la accuracy** | Alta | aceptado | El clasificador (TASK-010) acota candidatos por el grafo (clasificación jerárquica top-down y/o recuperación previa) en vez de volcar el árbol; acota el contenido enviado; valida toda propuesta contra el grafo y la confirma el curador; se mide la accuracy contra REAs ya catalogados. Detalle en `docs/superpowers/specs/2026-06-25-clasificador-ia-4b.md` |
| NFR-009 | Mantenibilidad y testeabilidad: el repo dispone en **GitHub Actions** de los flujos de CI/CD, revisión de código, pruebas y releases que automatizan la verificación y facilitan el mantenimiento y la seguridad del repositorio. Patrón de referencia: `ateeducacion/omeka-s-IsolatedSites` (`.github/workflows/`) | Media | aceptado | En `.github/workflows/` existen, como mínimo: (a) **CI** en cada `pull_request` y `push` que ejecuta `composer install` y los targets reales del Makefile —`make check-untranslated`, `make compile-mo`, `make lint` (PSR-12) y `make test`— sobre **PHP 8.4** (NFR-007); (b) **release** automatizado al publicar un tag `v*.*.*`: genera notas desde el historial, empaqueta con `make package VERSION=…` y crea la GitHub Release con el ZIP, usando el `GITHUB_TOKEN` nativo; (c) apoyo a la **revisión de código** en PR (p. ej. preview en Omeka-S Playground y/o revisión de seguridad/dependencias). Ningún workflow expone secretos (CLAUDE.md §Seguridad) ni modifica el core (NFR-001) |
